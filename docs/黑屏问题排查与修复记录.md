# 场景全黑问题：排查与修复记录

> 记录一次「整个场景渲染为纯黑，只有天空穹顶可见」的缺陷定位过程、根因与修复。
> 这个缺陷的特点是**只在真实 GPU 上复现**，软件渲染（SwiftShader）完全正常，
> 因此常规的无头测试全部给出「正常」的假象，排查一度指向错误方向。

---

## 一、现象

打开 `http://127.0.0.1:5173/` 后：

- 画面主体（建筑、地面、道路、道具、工人、车辆）**全部为纯黑**
- **只有天空穹顶正常显示**，能看到渐变天色和太阳光晕
- UI 界面（面板、时间轴、镜头按钮）全部正常
- 控制台无红色报错；`window.__CITY__` 存在，应用启动流程完整
- 时间/天气/镜头等交互均正常响应，只是看不到任何东西

关键对照：

| 渲染后端 | 结果 |
|---|---|
| 真实 GPU（ANGLE / AMD Radeon Graphics / D3D11） | **全黑** |
| SwiftShader 软件渲染 | **完全正常**，彩色画面 |

## 三、排查过程

### 3.1 先排除基础设施

第一反应是驱动、显卡或浏览器问题，但很快被否定：

- 另有一台电脑上的相同表现 → 不是单机环境问题
- 手写一个最小对照页，依次放置 4 个方块：
  1. `MeshBasicMaterial`（不参与光照）
  2. `MeshStandardMaterial` + 平行光 + 环境光
  3. `MeshStandardMaterial` + 光照 + 有限 near/far 的雾
  4. `MeshStandardMaterial` + 光照 + `PMREMGenerator` 环境贴图

  **4 个方块全部正常显示**，配合 ACES 色调映射 + sRGB 输出也正常。

结论：浏览器、GPU 驱动、Three.js 基础光照/雾/环境贴图链路都没有问题，
问题出在项目自身的某个具体设置上。

### 3.2 数据体检：几何与材质

写探针扫描整个场景（58 个 mesh）：

```
零长度法线       0
NaN position     0
NaN normal       0
NaN color        0
NaN uv           0
材质参数 NaN     0
```

几何数据完全干净，法线全部为单位向量，没有零填充属性。

### 3.3 灯光运行时 dump

```
DirectionalLight  强度 3.12   颜色 #fff3db   visible=true   （太阳）
DirectionalLight  强度 0.00   颜色 #9fb6e0   visible=true   （月亮，白天为 0 属正常）
HemisphereLight   强度 0.64   颜色 #c0d9f0   visible=true
AmbientLight      强度 0.25   颜色 #8a9db7   visible=true
DirectionalLight  强度 0.37   颜色 #dfe9ff   visible=true   （补光）
```

灯光强度、颜色、可见性全部正常，`layerMask` 与相机都在第 0 层，天空 uniforms 也是白天亮色。

### 3.4 第一个真实缺陷：雾参数 NaN（已修复，但不是根因）

`config/lighting.json` 里每个时刻的 `fog` 对象**只有 `color`，没有 `near`/`far`**：

```json
"fog": { "color": "#cfe0ee" }
```

而 `LightingSystem` 直接拿它做算术：

```js
fogNear: (this.weatherFogNear ?? 60) * lerp(1, a.fog.near / 100, 0.2),
fogFar:  (this.weatherFogFar ?? 240) * lerp(1, a.fog.far / 240, 0.2),
```

`undefined / 100` → `NaN`，于是 `fogNear` / `fogFar` 变成 `NaN`，
最终 `smoothstep(NaN, NaN, depth)` 污染 `mix()`。

这**确实是一个真实缺陷**，也修掉了，但修完之后**画面仍然全黑** → 它不是根因。

### 3.5 错误方向的代价

期间尝试并否定了大量假设（全部无效）：

| 尝试 | 结果 |
|---|---|
| 提高灯光强度 ×10 | 无效（且该测试本身无效，每帧 `apply()` 会覆盖） |
| 材质 `emissive` 改红色 | 仍全黑 |
| `?env=0` 关闭环境贴图 | 无效 |
| `?tonemap=none` 关闭色调映射 | 无效 |
| `?fog=0` 彻底移除雾 | 无效 |
| `?sky=off` 关闭天空穹顶 | 无效 |

**这里有一个重要教训**：阴影这条线索其实是最早被怀疑的，但因为在真实 GPU 上
缺少验证手段，被错误地提前搁置了。事后证明它才是真正的根因。

### 3.6 用「材质整体替换」一刀切开问题域

关键突破是加了一个临时诊断参数 `?basic=1`，把全场景材质整体替换为无光照的
`MeshBasicMaterial`：

```js
scene.overrideMaterial = new THREE.MeshBasicMaterial({ color: 0xff6600 });
```

**结果：整个场景变成明亮的橙色，几何轮廓、遮挡关系、深度排序全部正确。**

这一步的价值在于一刀切分：

- 几何体数据 ✅、相机 ✅、投影矩阵 ✅、深度测试 ✅、雾 ✅、色调映射 ✅
- 唯一剩下的嫌疑：**受光材质（`MeshStandardMaterial`）的着色链路**

### 3.7 在干净受光材质上逐项做二分

接着用一份「尽可能干净」的 `MeshStandardMaterial` 做 `overrideMaterial`
（关闭顶点色、全部贴图、自发光、环境贴图强度，`metalness=0`，`roughness=1`，
`side=DoubleSide`，`fog=false`），同时关掉 `scene.environment` 和阴影：

**结果：画面是明亮的绿色，完全正常。**

然后在这个干净基线上逐项恢复设置：

| 恢复项 | 结果 |
|---|---|
| 打开 `renderer.shadowMap.enabled` | **立刻全黑** ← 命中 |
| 恢复 `scene.environment`（`envMapIntensity=0`） | 正常 |
| 恢复 `envMapIntensity=1` | 正常 |
| 恢复项目原始材质（env 开、阴影开） | 全黑 |
| 恢复项目原始材质（env 开、阴影关） | 正常 |

结论明确：**只要打开阴影就全黑，关掉阴影就正常。**

### 3.8 读到阴影贴图的真实参数

打印 `sun.shadow` 的实际状态：

```
shadowMap.type          PCFSoftShadowMap
sun.castShadow          true
mapSize                 [null, null]        ← 注意这里
bias                    -0.0006
normalBias              0.06
shadow.camera           left/right/top/bottom = ±72, near=1, far=360
sun.position            [70.5, 110.77, -80.3]
sun.target.position     [0, 4, -2]
```

`mapSize` 是 `[null, null]` —— 在 `JSON.stringify` 里 `undefined` 会被序列化成
`null`，所以这两个值实际上是 **`undefined`**，而不是 `2048`。

### 3.9 控制台给出了决定性证据

打开浏览器控制台日志捕获后，出现大量重复报错：

```
GL_INVALID_FRAMEBUFFER_OPERATION: glClear: Framebuffer is incomplete: Attachment has zero size.
GL_INVALID_FRAMEBUFFER_OPERATION: glDrawArrays: Framebuffer is incomplete: Attachment has zero size.
GL_INVALID_FRAMEBUFFER_OPERATION: glDrawArraysInstanced: Framebuffer is incomplete: Attachment has zero size.
```

**根因彻底坐实。**

## 四、根因

阴影贴图的尺寸被写成了 `undefined`，导致阴影渲染目标变成 **0×0**。

### 4.1 缺陷链路

**第 1 步** — `src/app.js:117` 传入的画质预设是残缺的，**没有 `shadowMap` 字段**：

```js
this.world.setQuality({ pixelRatio: this.engine.quality.pixelRatio, shadows: true, aa: true });
//                                                                          ^^^^^^^^^^^^^^^^
//                                                                           缺少 shadowMap
```

**第 2 步** — `src/World.js:532` 无条件把它写进阴影贴图尺寸，守卫条件形同虚设：

```js
if (this.lighting.sun.shadow.mapSize.width !== preset.shadowMap) {
//     2048                          !== undefined  →  条件为 true，守卫失效
  this.lighting.sun.shadow.mapSize.set(preset.shadowMap, preset.shadowMap);
//                                    set(undefined, undefined)
```

**第 3 步** — 阴影渲染目标尺寸归零 → framebuffer incomplete：

```
GL_INVALID_FRAMEBUFFER_OPERATION: Framebuffer is incomplete: Attachment has zero size.
```

**第 4 步** — 阴影深度贴图永远渲染不进去。真实 GPU 采样到无效深度，
把每个受光片元都判定为「处于阴影中」，平行光的贡献被清零，
于是所有 `MeshStandardMaterial` 渲染为纯黑。

### 4.2 为什么天空穹顶是唯一幸存者

天空穹顶使用的是自定义 `ShaderMaterial`
（见 `src/core/SceneManager.js` 的 `_buildSkyDome()`），它：

- 不参与标准光照管线，直接输出 `gl_FragColor`
- `depthWrite = false`
- 不采样阴影贴图

所以整条坏掉的链路完全绕过了它，这就解释了「只有天空可见」这个极具迷惑性的现象。

### 4.3 为什么只在真实 GPU 上复现

这是本缺陷最坑的地方：

**SwiftShader 软件光栅器会容忍 incomplete framebuffer** —— 报错照报，
但阴影采样返回 0，视觉效果上反而接近「没有阴影」，画面正常出彩色。

真实 GPU 驱动则会严格执行，采样到无效值后整个受光计算被污染。

因此：

- 所有无头 / 软件渲染的自动化测试 → 全部显示「正常」
- 只有真实 GPU 上的用户 → 看到全黑

这也解释了为什么问题表现为「换台电脑也一样」——
它跟具体机器无关，只跟「是否走真实 GPU 路径」有关。

## 五、修复

### 5.1 主修复：`src/World.js`

只在调用方**确实提供了合法尺寸**时才重设阴影贴图：

```js
this.renderer.shadowMap.enabled = preset.shadows !== false;
// Only resize the shadow map when the caller actually asked for a size. A
// partial preset (e.g. { pixelRatio, shadows: true }) leaves
// preset.shadowMap undefined, and writing that into mapSize zeroes the
// shadow render target. The framebuffer is then incomplete, the depth
// texture never renders, and on real GPUs every lit surface samples as
// fully shadowed — the whole scene turns black while the unlit sky dome
// survives. Software rasterisers tolerate it, so it only shows up on real
// hardware.
const shadowMapSize = Number(preset.shadowMap);
if (Number.isFinite(shadowMapSize) && shadowMapSize > 0 && this.lighting.sun.shadow.mapSize.width !== shadowMapSize) {
  this.lighting.sun.shadow.mapSize.set(shadowMapSize, shadowMapSize);
  if (this.lighting.sun.shadow.map) {
    this.lighting.sun.shadow.map.dispose();
    this.lighting.sun.shadow.map = null;
  }
}
```

设计要点：

- `Number(preset.shadowMap)` 统一处理 `undefined` / `null` / 字符串
- `Number.isFinite() && > 0` 双重校验，杜绝 `undefined`、`NaN`、`0`、负数
- 尺寸未变化时不做任何操作，避免无谓的贴图重建
- 保留原有的 `dispose()` 逻辑，防止显存泄漏

### 5.2 附带修复：`src/systems/LightingSystem.js`

修掉 3.4 节发现的独立 NaN 缺陷：

```js
fogNear: (this.weatherFogNear ?? 60) * lerp(1, (a.fog.near ?? 100) / 100, 0.2),
fogFar:  (this.weatherFogFar ?? 240) * lerp(1, (a.fog.far ?? 240) / 240, 0.2),
```

它**不是**全黑的原因，但同属「配置缺字段 → NaN → 污染着色器」这一类缺陷，
且 `config/lighting.json` 确实只定义了 `fog.color`，所以必须加兜底。

## 八、经验教训

### 8.1 「配置缺字段」是本项目的高频缺陷模式

本项目已经出现过多次同类问题，模式完全一致：

```
配置对象缺少某个字段
  → 代码做算术运算（undefined / 100）
  → 得到 NaN
  → NaN 传入着色器 uniform
  → 污染 mix() / smoothstep() / 光照累加
  → 画面全黑
```

**教训**：所有影响最终渲染的参数，都必须在读取时提供默认值或兜底逻辑。
不要假设配置文件一定写全了字段。

### 8.2 软件渲染通过 ≠ 真实 GPU 通过

这是本次排查最大的教训。SwiftShader 对不规范状态的**容忍度显著高于真实驱动**：

- incomplete framebuffer → SwiftShader 照常渲染，真实 GPU 全黑
- NaN 传播 → SwiftShader 可能返回 0，真实 GPU 传播 NaN

**教训**：涉及 WebGL 状态、framebuffer、NaN 的问题，
**必须**在真实 GPU 路径上验证。软件渲染的「通过」不具备证明力。

同时要注意：本机早期尝试用无头 Edge 的 GPU 通道截图时，
通道本身是坏的（`glError 1286`，连天空都采样为 0），
这种「工具本身不可信」的情况下得到的任何数值都不能作为判断依据。

### 8.3 二分法要选对「切面」

排查之所以能收敛，靠的是两次正确的一刀切：

1. **整体替换材质**（`overrideMaterial` 换成无光照材质）
   —— 瞬间切分「几何/相机/深度/雾/色调映射」与「光照着色」
2. **在干净材质上逐项恢复设置**
   —— 把十几个可疑设置压缩成一次线性二分

**教训**：当同时有多个可疑因素时，不要逐个「关掉试试」，
而应该先建立一个**已知良好的最小基线**，再往上一项一项加。
「从干净基线逐项加」比「从脏现场逐项删」的定位效率高得多。

### 8.4 不要忽视控制台里的 GL 错误

`GL_INVALID_FRAMEBUFFER_OPERATION` 这类错误其实一直在控制台里刷屏，
但早期排查时没有被采集。**教训**：WebGL 场景出问题时，
第一步就应该开启控制台日志采集（`Log.enable` / `Runtime.consoleAPICalled`），
底层 GL 报错往往能直接指向根因，比任何间接推断都快。

### 8.5 带 Guard 的条件判断要检查「守卫本身是否成立」

出问题的代码原本是有守卫的：

```js
if (this.lighting.sun.shadow.mapSize.width !== preset.shadowMap) { ... }
```

看起来像是「尺寸变了才重设」，但 `2048 !== undefined` 恒为 `true`，
守卫完全没有起到防护作用。

**教训**：写「变化才更新」这类 Guard 时，
必须同时校验**新值本身的合法性**，而不只是比较新旧值是否相等。
